# VEYRA — Project Identity

**Document ID:** VEYRA-00.1  
**Version:** 1.0  
**Status:** Canonical Working Document  
**Parent:** Phase 0 — Foundation / Constitution

## 1. Purpose

This document establishes the canonical identity of the Veyra project.

It defines the name, identity, fundamental classification, and relationship to the project's historical AION Builder designation.

It does not define Veyra's detailed architecture, implementation technologies, or final technical design.

## 2. Canonical Name

The canonical name of the software-engineering platform is:

**Veyra**

Repository:

**SemajLedif/VEYRA**

Veyra is the current and canonical project identity.

## 3. Historical Name

Before the project adopted the Veyra identity, the software-engineering platform was referred to as:

**AION Builder**

Existing design material may therefore contain the name "AION Builder."

Such material represents historical project knowledge and remains part of the project's design lineage.

When creating new canonical documentation, Veyra shall be used unless a historical reference specifically requires the former name.

## 4. Fundamental Identity

Veyra is a:

> **General-purpose autonomous software-engineering intelligence and software-production platform.**

Its fundamental purpose is not limited to generating source code.

Veyra is intended to coordinate the capabilities required to take software from an initial idea through the broader engineering lifecycle.

The intended lifecycle includes:

- research;
- discovery;
- requirements;
- planning;
- architecture;
- design;
- implementation;
- testing;
- debugging;
- verification;
- security;
- deployment;
- operations;
- maintenance;
- evolution.

Veyra therefore concerns software engineering as a complete process, rather than coding assistance as an isolated activity.

## 5. General-Purpose Nature

Veyra is not specifically a system for building AION.

Its purpose is to become a general software-engineering system capable of working across different software projects, technology stacks, architectures, and engineering requirements.

AION is one potential project that Veyra may eventually help construct.

Veyra must therefore be designed around the general problem of software production rather than around the requirements of a single software project.

## 6. What Veyra Is Not

Veyra is not fundamentally defined as:

- a conventional AI coding assistant;
- a chatbot that happens to generate code;
- a fixed collection of independent coding bots;
- a permanently fixed team of named AI agents;
- a system with a literal "100-agent" limit;
- an AION-specific development tool.

The "100 engineers" concept is understood as a metaphor for substantial coordinated engineering capability rather than a fixed numerical architecture.

## 7. Intelligence and Workforce Model

The intended Veyra model is based on coordinated engineering capabilities rather than a permanently fixed set of agents.

Conceptually:

```text
Capabilities
     ↓
Roles
     ↓
Workers
     ↓
Teams
     ↓
Departments
     ↓
Project Organization
```

A worker or agent may implement one or more capabilities.

The system should ultimately be capable of assembling and coordinating the capabilities required by a particular software project.

The exact mechanisms for workforce formation, coordination, communication, scheduling, and execution remain subjects for later research and architecture.

## 8. Software-Engineering Organization Concept

Veyra is intended to provide capabilities analogous to a large coordinated software-engineering organization.

This does not mean that Veyra is defined by literally simulating a fixed human company or by requiring a fixed number of artificial workers.

The organizational concept exists to express the desired ability to:

- divide complex engineering problems;
- assign appropriate capabilities;
- coordinate specialized work;
- manage dependencies;
- review results;
- detect failures;
- recover from failures;
- integrate outputs;
- continuously verify the resulting system.

The implementation of this concept remains open.

## 9. Model and Technology Independence

Veyra's identity is not tied to a particular:

- AI model;
- model provider;
- agent framework;
- programming language;
- software framework;
- database;
- cloud provider;
- execution environment;
- development tool.

The project baseline establishes a goal of model/provider independence and support for local, open-source, and free options where practical.

Specific technology decisions belong to later research and architecture phases.

## 10. Relationship to Software Projects

Veyra is intended to operate as an engineering system capable of working on arbitrary software projects.

A project supplied to Veyra may differ in:

- domain;
- programming language;
- framework;
- architecture;
- infrastructure;
- scale;
- security requirements;
- deployment model;
- testing requirements;
- operational requirements.

Veyra's general-purpose identity therefore requires the system to adapt its engineering capabilities to the project rather than forcing every project into one predefined technology or organizational structure.

## 11. Relationship to the Builder Foundry

The Builder Foundry is the development environment and engineering ecosystem used to construct Veyra itself.

This distinction is important:

**Veyra** is the software-engineering platform being built.

**The Builder Foundry** is the environment and process used to build it.

The Foundry may use Veyra and related engineering capabilities as the project develops, but the two concepts should not be treated as identical.

## 12. Identity Principle

The central identity principle is:

> **Veyra exists to provide general-purpose software-engineering intelligence and coordinated software-production capability, not merely code generation.**

Its ultimate value is measured by its ability to produce, verify, operate, maintain, and improve useful software.

## 13. Identity Boundaries

This document establishes identity only.

It does not establish:

- final system architecture;
- final agent architecture;
- final workforce hierarchy;
- final memory architecture;
- final orchestration architecture;
- final security architecture;
- final infrastructure;
- final commercial model;
- final technology stack.

Those matters remain governed by the Master Design Order and the appropriate later phases.

## 14. Status of This Identity

This document establishes Veyra as the canonical product identity for the project.

The historical term AION Builder remains valid when referring to earlier project material or historical decisions.

Future canonical documents should use Veyra.

## 15. Summary

Veyra is the general-purpose autonomous software-engineering platform within the broader AION vision.

Its purpose is to develop software-engineering capability that can operate across the complete software lifecycle and across diverse software projects.

The project is therefore fundamentally concerned with:

> **Turning software ideas into reliable, tested, secure, deployable, maintainable, and continuously improvable software through coordinated intelligence and engineering automation.**
